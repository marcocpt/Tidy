# Tidy 编码规范

> 最后更新：2026-07-28 | 版本：v0.1
> 文档状态：草案
> 适用范围：Tidy 仓库所有 Swift 代码（TidyCore / TidyUI / TidyApp）

本文档是 Tidy 项目的编码写法契约，定义缩进、命名、日志、并发、错误处理、魔术数字消除和测试的统一规则。架构分层与依赖方向见 [全局架构契约](../architecture/Tidy_全局架构契约.md)，本文档不重复。

## 1. 语言风格

### 缩进与格式

- 缩进：4 空格，不使用制表符
- 行宽上限：120 字符
- 大括号：K&R 风格（右大括号独占一行，else/catch 等与右大括号同行）
- 每个文件末尾保留一个空行
- 文件内类型声明之间保留一个空行

### 命名约定

| 类别 | 风格 | 示例 |
|------|------|------|
| 类型（类、结构体、枚举、协议） | PascalCase | 窗口枚举器、编排协调器 |
| 方法 | camelCase，动词开头 | 枚举窗口、排列窗口 |
| 变量与属性 | camelCase | 窗口列表、当前状态 |
| 常量 | camelCase（局部）或 PascalCase（全局） | 默认热键码、最大窗口数 |
| 枚举成员 | camelCase | 空闲、排列中、选择中 |
| 协议（描述能力） | 名词 + 后缀 | 窗口枚举协议、权限检测协议 |
| 协议（描述行为） | 动词 + 后缀 | 编排协议 |
| 文件名 | 与主类型名一致 | — |
| 测试方法 | 全描述性，下划线分隔 | test_排列两个窗口时_应生成网格布局 |

### import 规则

- 每个文件只导入直接使用的框架
- 系统框架在前，第三方框架在后，项目模块最后，各组之间空一行
- 禁止使用通配符导入

## 2. 文档注释

- 公共 API（被其他模块使用的类型、方法、属性）必须有文档注释
- 文档注释使用 `///` 格式
- 注释描述"做什么"和"为什么"，不描述"怎么做"
- 复杂内部逻辑（状态机转换条件、布局算法分支、权限检测时序）需简洁说明
- 禁止无意义注释（如重复方法名的注释）
- 禁止注释掉的代码；不再需要的代码直接删除，通过 Git 历史追溯

## 3. 日志规范

- 使用项目日志子系统，不写死具体日志器类名
- 日志子系统标识：项目统一标识符
- 关键节点（编排开始、状态转换、权限变化、窗口操作）使用信息级
- 辅助功能操作失败、状态机非法转换使用错误级
- 日志不输出：用户输入内容、含用户名的路径、窗口标题中的个人信息
- 错误级日志必须附带上下文元数据：操作类型、目标应用标识、当前状态
- 探针与测试代码允许临时使用简单打印，进入生产模块前必须替换

## 4. 并发规范

- UI 状态更新必须在主线程执行
- 辅助功能操作（窗口枚举、窗口移动）在主线程执行（系统要求）
- 长时间计算（布局算法、大量窗口枚举）使用异步任务
- 并发协调使用项目异步运行时，不手动创建调度队列
- 状态机状态变更必须在主线程，确保线程安全
- 禁止数据竞争：共享可变状态必须受并发原语保护
- 响应式 UI 绑定使用项目响应式框架

## 5. 错误处理

- 不吞掉错误：每个错误都必须有至少一个处理路径（日志、恢复、传播）
- 辅助功能操作失败：记录错误级日志，按架构契约的失败处理策略降级
- 状态机非法转换：触发错误级日志，回退到安全状态
- 错误需可检索：关键错误类型使用项目错误域，附带错误码和上下文
- 预期缺失（如窗口已关闭、应用已退出）使用可选值返回，不抛异常
- 非预期错误（如系统接口异常）使用抛出机制
- 禁止空 catch 块；至少记录日志

## 6. 魔术数字与魔术字符串

- 系统键码、框架常量使用命名常量
- 阈值（失败率、超时时间、最大窗口数）使用命名常量
- 配置键使用命名常量
- 布局参数（间距、边距、标签尺寸）使用命名常量
- 命名常量集中定义在所属模块的常量区域，不散落在方法体内
- 禁止在代码中直接使用数字字面量（0 和 1 除外，用于索引和布尔转换）

## 7. 测试规范

- 测试框架：项目单元测试框架 + UI 测试框架
- 新功能优先编写测试（测试驱动）
- Mock 只模拟外部依赖（系统框架、其他模块的协议），不 mock 被测对象本身
- 测试隔离：每个测试独立运行，不依赖其他测试的副作用
- 测试命名：全描述性，说明前置条件和预期结果
- 状态机测试：必须覆盖所有合法转换和至少一个非法转换
- 布局算法测试：必须覆盖边界值（0、1、2、9 个窗口）
- 辅助功能兼容性测试：记录为证据，不在单元测试中模拟系统行为

## 8. 验证命令

| 命令 | 用途 | 执行条件 |
|------|------|---------|
| `swiftlint lint --strict` | 代码风格检查 | 每次提交前 |
| `swift build` | 编译检查 | 每次变更后 |
| `swift test` | 运行测试 | 实现变更后 |

### Greenfield 质量政策

- 新代码零新增 lint error
- 新代码零新增 lint warning（确实无法修复时写入配置并附理由）
- 测试必须通过
- 配置文件建立前，提交前至少运行默认规则并人工复核
