# Tidy 窗口管理 App 市场调研报告

> 最后更新：2026-07-25 | 版本：v1.1

> 当前名称：**Tidy 仅作为工作名，正式发布前必须完成改名、商标、域名与商店检索**
>
> 调研范围：macOS 系统能力、主流窗口管理器、窗口切换器、窗口提示工具，以及 Power User 常见多窗口场景

## 一、执行摘要

### 结论

**Tidy 有市场前景，值得继续，但更适合定位成“小而强、可盈利的 macOS 独立工具”，而不是能够自然扩张成大公司的平台型产品。**

| 维度 | 判断 |
|------|------|
| 用户痛点 | 较真实，集中在 Xcode、VS Code、Finder、浏览器等同一 App 多窗口场景 |
| 产品差异化 | 有，但不是“字母标签”或“窗口管理”本身，而是临时编排与撤回的完整闭环 |
| 技术可行性 | 可行；AX 窗口移动、速度与还原可靠性决定产品成败 |
| 竞争压力 | 高；Ankylix、JINRAI 等新工具已覆盖字母提示和键盘选窗 |
| 付费潜力 | 中等，适合买断制与全功能试用 |
| 总体建议 | **继续，但先做极小验证版，不直接按完整 v1.0 开发** |

Tidy 最值得验证的不是笼统的“窗口管理”，而是这条工作流：

> 临时铺开 → 看清窗口 → 键盘选择 → 专注工作 → 撤回原布局。

这条闭环与 Rectangle、Moom 等以固定布局为中心的工具仍有差异，也与 Ankylix、JINRAI 等以原位置提示或通用窗口操作为中心的工具不同。但竞争壁垒没有“首个字母选窗工具”那么宽，必须通过速度、兼容性和还原可靠性建立。

### 现阶段最重要的五项决策

1. 将 “Tidy” 降级为工作名，公开测试前完成改名。
2. v0.1 只覆盖当前屏幕、前台 App、2～9 个可见窗口。
3. 默认不把多屏窗口聚合到一个屏幕。
4. AX 移动失败时降级为原位置标签选择，而不是直接退出。
5. 先用 15～30 名目标用户验证两周，再决定是否进入完整 v1.0。

## 二、项目定位与核心假设

### 项目愿景

打造一个键盘驱动的 macOS 窗口临时编排工具，让多窗口工作者能完成：

> 展开一个 App 的当前窗口 → 选中要工作的窗口 → 完成后原样归位。

核心理念：

> 像临时摊开桌面资料一样展开窗口；找到目标后专注工作；结束时撤回这次临时改动。

### 调研目标

1. 验证“临时真实窗口重排 + 标签选择 + 自动快照撤回”是否构成可感知差异。
2. 识别系统能力、传统窗口管理器和新兴窗口提示工具带来的竞争压力。
3. 找出会决定留存的核心体验指标，而不是以功能数量衡量 MVP。
4. 校准 MVP 范围、恢复语义、商业模式与继续开发门槛。
5. 识别命名、分发、权限、兼容性和多显示器风险。

### 第一目标用户：同一 App 多窗口工作者

典型人群：

* 开发者：多个 Xcode、VS Code、JetBrains、终端或浏览器窗口
* 设计师：多个 Figma、Photoshop 或素材窗口
* 写作者与研究员：多个浏览器、文档、Finder 窗口
* PM 与运营：多个浏览器、Slack、文档窗口

核心场景：

> 同一 App 有 3～8 个窗口，用户想快速看清并选择其中一个，又不想永久改变原布局。

| 特点 | 说明 |
|------|------|
| 切换频率高 | App 级 Cmd+Tab 无法直接解决同 App 多窗口选择 |
| 愿意为效率付费 | macOS Power User 是主要付费人群 |
| 对稳定性敏感 | 一次错误还原就可能失去信任 |
| 反馈价值高 | 能明确描述 Xcode、Electron、浏览器等兼容问题 |

### 次级用户：多显示器 Power User

多屏用户有真实痛点，但他们往往有意维持“代码在主屏、资料在副屏”的空间关系。因此，多屏不是 v0.1 的默认聚合场景，而是后续验证方向：

1. 默认：只处理焦点所在屏幕的窗口。
2. 可选：同一 App 各屏窗口在各自屏幕内排列。
3. 高级选项：将同一 App 窗口临时聚合到焦点屏。

### 不作为 MVP 核心的用户

只偶尔开两个窗口、主要依赖鼠标、或希望长期自动平铺全部桌面的用户，不是首轮验证对象。他们已有 macOS 原生平铺、Rectangle、Magnet、Amethyst 等成熟选择。

### 核心问题

Tidy 要验证的不是“用户是否需要管理窗口”，而是：

> 用户是否愿意让工具临时移动一组窗口，以换取更清晰的识别与更快的选择，并相信它能可靠撤回。

产品的优势和最大风险来自同一个动作：**先移动窗口**。

## 三、竞争格局

### 调研边界

竞品分为四类：

1. macOS 系统内置窗口与工作区能力
2. 传统窗口摆放、平铺与布局恢复工具
3. 窗口切换器
4. 字母提示与键盘窗口操作工具

价格、版本和维护状态会变化，本文仅用于产品决策，不替代发布前的再次核验。

### 系统内置能力

| 能力 | 定位 | 优势 | 与 Tidy 的差异 |
|------|------|------|----------------|
| App Exposé | 查看单个 App 的窗口 | 系统原生、无需权限 | 以缩略图浏览为主，不提供 Tidy 的临时真实窗口重排与快照撤回 |
| Mission Control | 全局窗口与 Space 鸟瞰 | 系统原生、覆盖全局 | 面向全局导航，不是同 App 临时编排闭环 |
| Stage Manager | 持续性的工作区分组 | 可排列、组合多个 App | 面向持续分组；Tidy 面向临时、键盘驱动、可撤回的同 App 多窗口选择 |
| 原生窗口平铺 | 单窗口或多窗口排列 | 系统持续增强、无需第三方工具 | 解决摆放，不自动完成“展开—选择—撤回” |

不再使用“Stage Manager 仅主屏、外接屏无效”的表述。Apple 当前文档要求开启“显示器具有单独的空间”才能使用 Stage Manager，并支持排列窗口和组合多个 App。Tidy 应通过不同工作流定位自身，而不是依赖贬低系统能力。

### 传统窗口管理与布局恢复

| 产品 | 核心能力 | 与 Tidy 的关系 |
|------|----------|----------------|
| Rectangle / Rectangle Pro | 快捷键摆放、保存布局、单步撤销 | 强大的通用窗口操作；不以临时展开同 App 窗口为核心 |
| Magnet / BetterSnapTool / Swish | 拖拽、快捷键或手势摆放窗口 | 解决单窗口位置管理 |
| Moom | 自定义动作、保存布局、Any-Window Layouts | 可影响最近 N 个窗口，但通常需要预设布局 |
| Stay | 按显示器组合保存与恢复布局 | 解决长期布局恢复，不解决快速识别与选择 |
| Amethyst / yabai | 持续自动平铺 | 面向常驻平铺工作流，不是按需临时编排 |

Apple 原生窗口平铺与“恢复到之前的窗口大小”能力持续增强，普通“摆窗口”越来越难成为独立卖点。Tidy 必须聚焦临时编排和撤回体验。

### 窗口切换与字母提示

| 产品 | 选择方式 | 已覆盖能力 | Tidy 仍可区分的部分 |
|------|----------|------------|----------------------|
| Contexts | 搜索、列表、侧栏 | 跨 App 窗口切换 | 不临时重排真实窗口 |
| Witch | 列表、搜索、数字直跳 | 成熟窗口切换 | 不临时重排真实窗口 |
| rcmd / HopTab 等 | 快捷键或搜索 | 键盘驱动切换 | 更偏轻量切换器 |
| **Ankylix** | 给可见窗口和布局区域显示字母提示 | 聚焦、移动、调整与平铺 | 没有以自动快照和临时展开后撤回为核心 |
| **JINRAI Window Hints** | 窗口按键提示 | 可覆盖其他 Space、遮挡窗口，并提供多窗口布局 | 更偏通用窗口操作与提示，不以临时撤回闭环为中心 |

### 名称直接冲突：Window Tidy

Mac App Store 已有一款名为 **Window Tidy** 的窗口布局工具，通过拖放到可配置网格来排列窗口。即使最终不构成法律冲突，也会造成：

* 商店与搜索结果混淆
* 用户误认和口碑归属不清
* 域名、SEO 与社交账号难获取
* 媒体报道和应用推荐难区分

因此，“Tidy”只能作为内部工作名，不应直接进入正式品牌阶段。

### 关键发现

#### 发现 1：字母标签不是市场空白

Ankylix 和 JINRAI 已证明“窗口上显示按键提示、看到即输入”不是 Tidy 独占能力。以下表述应废弃：

> 首个支持字母标签选择窗口的产品。

更准确的定位是：

> 专注“临时真实窗口重排 + 标签选择 + 自动快照撤回”闭环的产品。

#### 发现 2：差异仍然存在，但必须由体验证明

现有能力大多分散在不同产品中：

| 需求 | 常见方案 | 未完全解决的问题 |
|------|----------|------------------|
| 看见多个窗口 | App Exposé / Mission Control | 主要是缩略图与系统级导航 |
| 用键盘选窗口 | Ankylix / JINRAI / Witch / Contexts | 多数不先临时展开真实窗口 |
| 改变窗口布局 | Rectangle / Moom / 平铺管理器 | 多数是持久或预设布局 |
| 恢复布局 | Stay / Moom / Rectangle Pro | 多数需要预先保存或配置 |

Tidy 的机会是把这些步骤压缩成一次无需预配置的临时会话，而不是宣称每个单项能力都无人实现。

#### 发现 3：不存在可靠的“6～12 个月无人竞争窗口”

新工具已经快速接近字母提示、布局和键盘控制的交集。先发优势不应写成确定性结论。可持续优势只能来自兼容性数据、还原成功率、速度和默认体验。

## 四、市场机会与产品壁垒

### 最有价值的细分机会

Tidy 面向一个明确而有限的场景：

> 用户没有预先配置布局，只想临时看清前台 App 的几个窗口，选一个工作，之后撤回本次编排。

这是有真实需求、竞争密集、但仍有细分体验空位的 macOS Power User 工具市场。

### 真实窗口的价值边界

“真实窗口比缩略图更易识别”只在窗口数量适中时成立。普通 14～16 英寸屏幕无法保证 13～26 个窗口内容仍然可读。

| 窗口数量 | 建议行为 |
|----------|----------|
| 2～9 | 完整真实窗口网格；核心场景 |
| 10～16 | 后续评估网格 + 标题 + App 图标、分页或双字符标签 |
| 17 个以上 | 不再承诺全部移动；考虑搜索、分页或仅标签切换 |

因此，“26 个窗口内内容可读”和“a-z 全覆盖”不再作为卖点。核心用户更可能是同一 App 同时打开 3～8 个窗口。

### 最大体验风险：移动本身造成打断

用户只是想找一个窗口时，Tidy 可能执行：

1. 保存多个窗口的位置和大小。
2. 移动并调整多个窗口。
3. 选择一个窗口并临时放大。
4. 最终再次移动全部窗口完成还原。

如果过程中出现等待、跳动、重绘或恢复偏差，Tidy 会比轻量切换器更打断工作。因此核心指标不是功能数量，而是：

* 热键按下后立即出现可感知反馈。
* 2～9 个窗口排列过程没有明显等待或反复跳动。
* Chrome、Xcode、Finder、Office、Electron 与 JetBrains 应用表现可预测。
* 不丢屏幕、不意外改变最小化状态。
* 位置与大小还原成功率达到可建立信任的水平。

### 真正值得构建的四项壁垒

1. **兼容性数据库**：记录不同 App 设置 frame、等待、重试和聚焦的实际行为。

2. **还原可靠性**：任何一个窗口恢复错误都可能直接破坏用户信任。

3. **速度与过渡体验**：用户按下热键后应立即收到视觉反馈；排列不应让人感觉“窗口炸开再缩回”。

4. **无需配置的默认体验**：不要求预建 Layout、记忆窗口名或编写配置文件。

产品文案应从“键盘驱动的窗口管理工具”收敛为：

> 临时展开一个 App 的窗口，选中要工作的那个，完成后原样归位。

## 五、v0.1 产品策略

### 验证目标

v0.1 只回答一个问题：

> 目标用户是否会反复使用“铺开—选择—还原”，并认为它比 App Exposé 或普通窗口切换器更快？

### 默认作用域

* 当前焦点所在屏幕
* 前台 App
* 当前 Space 中 2～9 个可见、可操作窗口
* 单次会话
* 一个固定热键

默认不跨屏搬运窗口，不处理最小化窗口，不承诺全屏窗口，不持久化崩溃前快照。

### 核心流程

```text
按 Tidy 热键
  → 保存当前屏幕内前台 App 窗口的位置和大小
  → 将 2～9 个窗口临时排成网格
  → 在每个窗口中心偏上位置显示按键标签
  → 用户按字母，目标窗口临时放大
  → 用户工作
  → 按 Tidy 热键或 Esc
  → 恢复本次会话记录的位置和大小
```

### 选中后的动作

产品应在内部保留三种策略，以便通过测试比较：

| 策略 | 行为 | 适用场景 |
|------|------|----------|
| Focus | 只聚焦目标窗口，维持当前网格 | 用户仍需对照其他窗口 |
| Temporary Maximize | 临时放大目标窗口，稍后还原 | 当前 MVP 默认实验 |
| Bring Forward | 恢复原始布局，只将目标窗口置前 | 用户只想找到窗口，不想全屏 |

v0.1 默认采用 **Temporary Maximize**，但必须在用户测试中验证。可将 `Shift + 字母` 作为 Focus 实验入口，不在首轮设置界面暴露复杂配置。

### 标签位置

不再将标签固定在窗口左上角 `(8, 8)`。该位置与 macOS 红黄绿窗口按钮直接冲突。

默认位置：

> 窗口中心偏上，避开系统控制按钮，并根据可见 frame 动态约束在屏幕内。

网格只短暂存在，少量覆盖内容比遮挡关闭、最小化和全屏按钮更可接受。

### AX 失败降级

如果部分窗口不允许修改 frame：

1. 不直接退出整个会话。
2. 保留窗口原位置。
3. 在原窗口可见区域显示标签。
4. 将本次会话降级为“仅标签窗口切换器”。
5. 向用户提供简短、非打断式状态提示。

这使 Tidy 在 Logic Pro、Final Cut Pro 或其他兼容性较差的 App 中仍可能有用，也能将核心编排失败转化为可用的降级体验。

### 自动还原规则

| 事件 | 默认行为 |
|------|----------|
| 再按 Tidy 热键 | 还原 |
| Esc | 还原 |
| Space 切换 | 还原，避免跨 Space 坐标与窗口归属错误 |
| 目标 App 退出 | 清理会话；能恢复的窗口尽力恢复 |
| 切换到其他 App | **暂不还原** |
| selecting 阶段超时 | 还原 |
| working 阶段超时 | 不启用 |

“切换 App 自动还原”可在验证后作为可选设置，不作为默认行为。用户临时切到 Safari 查资料时，不应因此丢失刚建立的工作状态。

### “还原”的明确语义

Tidy v0.1 的“还原”是：

> 恢复本次会话所记录窗口的位置和大小。

不保证恢复：

* 窗口层级和完整 z-order
* 原生标签页变化
* 全屏状态
* 最小化窗口状态
* App 内部布局或文档状态
* 会话期间由用户或 App 主动创建、关闭的窗口

v0.1 默认只处理可见、非全屏窗口，因此不应主动改变最小化状态。营销文案必须避免“无损恢复全部窗口状态”等过度承诺。

## 六、技术可行性与分发风险

### 核心能力

| 能力 | 建议方案 | 主要风险 |
|------|----------|----------|
| 全局热键 | Carbon RegisterEventHotKey | 快捷键冲突 |
| selecting 输入 | CGEventTap，仅会话期间启用 | Input Monitoring、tap 被系统禁用 |
| 窗口枚举 | CGWindowList + AXUIElement | AX 与窗口信息映射 |
| 窗口移动与缩放 | AXUIElement position + size | 不同 App 行为不一致 |
| 标签覆盖层 | AppKit 非激活面板 | 多屏坐标、层级与 Space |
| 目标屏判定 | 焦点窗口与 NSScreen 可见区域 | 边界窗口与坐标转换 |
| 会话快照 | 内存中的窗口 ID、位置和大小 | 窗口关闭、App 退出、崩溃 |

技术可行不等于体验可行。应先做真实 App 兼容性与性能探针，再决定完整架构。

### 必需权限

| 权限 | 用途 | v0.1 |
|------|------|------|
| Accessibility | 枚举、聚焦、移动和调整窗口 | 必须 |
| Input Monitoring | selecting 阶段读取全局按键 | 取决于最终事件方案，按必须权限设计验证 |
| Screen Recording | OCR 或窗口内容分析 | 不需要 |

权限完成率是首轮漏斗指标，首次启动必须解释用途并提供明确的授权状态。

### 分发

| 渠道 | 建议 | 原因 |
|------|------|------|
| 官网直售、公证签名、自动更新 | P0 | 更适合需要深度辅助功能与全局输入的工具 |
| Setapp | P1 | 产品稳定且完成付费验证后再评估 |
| Mac App Store | P2 | 沙盒、事件监听与审核能力需单独做技术验证 |

不要在技术验证前断言 Mac App Store 一定不可用，也不要为了上架而提前维护功能分叉版本。

## 七、MVP 范围与验证计划

### v0.1 保留与暂缓

| 保留 | 暂不做 |
|------|--------|
| 当前屏幕、前台 App、2～9 个窗口 | 跨屏聚合 |
| 保存窗口位置和大小 | 持久化崩溃恢复 |
| 自动网格 | 自定义布局模板 |
| 字母标签 | 字体、颜色和位置配置 |
| 字母选择后临时放大 | 应用专属 Profile |
| Esc / 热键还原 | working 循环切换 |
| AX 失败时降级为标签模式 | 复杂黑名单管理界面 |
| 一个固定热键 | 热键录制器 |
| 最小权限引导 | 完整偏好设置 |

状态栏图标只保留授权状态、启用/停用、退出和版本信息，不为 MVP 设计四种复杂状态或五项外观设置。

### 兼容性验证矩阵

优先覆盖：

* Xcode
* VS Code 与其他 Electron App
* Finder
* Safari 与 Chrome
* Microsoft Office
* JetBrains IDE
* Adobe 常用应用

每个 App 至少记录：

* 2、5、9 个窗口的排列时间
* 设置位置和大小的成功率
* 窗口是否产生重复跳动或明显重绘
* 临时放大与恢复的成功率
* AX 失败时标签降级是否仍可选择

### 继续开发门槛

找 15～30 个真正会同时打开多个 Xcode、VS Code、Finder 或浏览器窗口的用户，连续使用两周。

| 指标 | 建议门槛 |
|------|----------|
| 权限流程完成率 | ≥ 70% |
| 留存用户日均触发 | ≥ 5 次 |
| 两周后仍在使用 | ≥ 40% |
| 位置和大小还原成功率 | ≥ 99% |
| 2～9 个窗口排列完成时间 | P95 约 800ms 以内 |
| 明确愿意付费的测试者 | ≥ 20% |
| “比 App Exposé 更快”主观评价 | 多数用户认可 |

决策规则：

* 用户高频使用完整闭环：进入正式 v1.0。
* 用户喜欢字母选择，但很少使用铺开与还原：转向更轻量的窗口切换器。
* 还原成功率无法接近 99%：暂停商业化，先解决兼容性。
* 排列过程明显打断工作：优先验证 Bring Forward 或仅标签模式。

## 八、商业模式

### 市场惯例

窗口管理与 Power User 工具通常以买断为主。Ankylix 提供 14 天全功能试用和 €19 买断；Moom、Witch、Swish 等也位于相近的独立工具价格带。

### 推荐方案 A：全功能试用 + 买断

最适合独立开发者：

* 公测阶段免费。
* 正式版提供 14 天全功能试用。
* 定价 $12.99～$19.99 买断。
* 包含一年或一个大版本的功能更新。
* 已购买版本永久可用。
* 后续大版本可选择付费升级。

优点：

* 让用户完整体验真正差异化的闭环。
* 不需要人为削弱首次体验。
* 收费点与核心价值一致。
* 比订阅更符合该赛道预期。

### 备选方案 B：免费标签模式 + Pro 编排

如果确实需要永久免费版：

| 版本 | 内容 | 建议价格 |
|------|------|----------|
| 免费 | 原位置标签模式，只快速切换窗口 | $0 |
| Pro | 临时铺开、临时放大、还原、多屏与 Profiles | 约 $14.99 买断 |

“临时编排与撤回”应属于付费核心，而不是在免费版中完整赠送后，再依靠边缘设置转化。

### 不建议的方案

不建议继续采用：

> 免费版提供完整闭环，Pro $9.99 只销售应用专属设置、布局模板和循环切换。

它把最有价值的差异免费化，而剩余功能未必足以推动升级。

## 九、品牌与命名

### 当前判断

“Tidy”简洁且能表达整理感，但 **Window Tidy** 已经是现有 macOS 窗口工具名称。继续使用会带来明显的搜索和品牌成本。

### 发布前动作

1. 生成 20～30 个候选名。
2. 在 Mac App Store、主流搜索引擎、GitHub 与 Product Hunt 检索。
3. 检查主要域名和社交账号。
4. 在目标销售地区做商标近似检索。
5. 用 5～10 名目标用户测试发音、记忆和产品联想。

可探索的命名方向包括 TidyFlow、WindowFold、Unfold 等，但这些只是工作候选，不代表已经完成可用性、域名或商标验证。

## 十、主要风险

| 风险 | 说明 | 应对策略 |
|------|------|----------|
| 移动造成打断 | 铺开和还原比普通切换器动作更重 | 立即反馈、限制 2～9 个窗口、对比 Focus / Maximize / Bring Forward |
| AX frame 不稳定 | 部分 App 拒绝或延迟位置、大小修改 | 原位置标签降级、兼容性数据库、按 App 调整等待与重试 |
| 还原不可靠 | 任何一次位置或大小错误都会破坏信任 | 以 ≥99% 为门槛，完整记录失败层与 App |
| App 重绘与跳动 | Chrome、Xcode、Electron 等可能明显重排 | 批次策略、过渡节奏和真实设备性能测试 |
| 多显示器关系被破坏 | 聚合会破坏用户有意建立的屏幕分工 | v0.1 只处理当前屏幕 |
| Space 切换 | 窗口坐标和归属可能变化 | 切换前尽力还原并结束会话 |
| App 切换误还原 | 用户可能只是临时查资料 | 默认不因 App 切换还原 |
| 标签遮挡系统按钮 | 左上角与红黄绿按钮冲突 | 默认中心偏上，动态约束 |
| 高窗口数不可读 | 13～26 个真实窗口仍会过小 | v0.1 限制 2～9；后续用搜索或分页 |
| 权限流失 | Accessibility / Input Monitoring 会阻碍首次使用 | 清晰解释、状态检测、授权完成率门槛 |
| 系统能力增强 | Apple 持续增强平铺和窗口恢复 | 聚焦临时闭环，不与原生布局数量竞争 |
| 新竞品逼近 | Ankylix、JINRAI 已覆盖字母提示及更多操作 | 用可靠性、速度和无需配置建立壁垒 |
| 名称冲突 | Window Tidy 已存在 | 公测前改名并完成检索 |
| 付费转化不足 | 免费完整闭环会削弱 Pro 价值 | 优先全功能试用 + 买断 |
| 崩溃后无法恢复 | 内存快照会随进程丢失 | v0.1 明示边界；验证成功后评估持久化恢复 |

## 十一、阶段路线图

| 阶段 | 范围 | 退出条件 |
|------|------|----------|
| 技术探针 | AX 枚举、移动、聚焦、还原；覆盖重点 App | 证明 2～9 个窗口可在目标时间内可靠编排 |
| v0.1 内测 | 当前屏幕、单 App、标签、临时放大、还原、失败降级 | 15～30 人使用两周并达到继续门槛 |
| v1.0 | 打磨权限、兼容性、日志、更新与购买体验 | 可公开销售，核心恢复指标稳定 |
| v1.x | Focus / Bring Forward、多屏各自排列、应用 Profile | 由真实高频需求排序 |
| v2.0+ | 跨屏聚合、布局模板、持久化恢复 | 仅在核心闭环已验证后投入 |

不要在验证完成前承诺“跨 App 编排、复杂布局模板、Stage Manager 深度集成”等远期能力。

## 十二、最终定位

### 一句话产品定义

> 一个面向 macOS Power User 的临时窗口编排工具：展开一个 App 的窗口，选中要工作的那个，完成后原样归位。

### 与现有产品的根本差异

| 维度 | 常见产品 | Tidy 目标 |
|------|----------|-----------|
| 工作流 | 摆放、切换或恢复中的单点功能 | 临时铺开 → 选择 → 撤回 |
| 选择方式 | 鼠标、搜索、数字或原位置字母提示 | 临时展开后显示可见标签 |
| 布局前提 | 手动操作或预先保存 | 无需预配置，按会话自动快照 |
| 窗口状态 | 缩略图、列表或常驻平铺 | 2～9 个真实窗口按需排列 |
| 心智模型 | 管理窗口位置 | 临时摊开资料，完成后归位 |

### 最终判断

**建议继续，但以验证为先。**

应把预期从“发现了一个无人竞争的大市场”调整为：

> 发现了一个有真实需求、竞争密集、但仍有细分体验空位的 macOS Power User 工具。

做好后，它有机会成为一款口碑良好、能够稳定产生收入的独立产品；做成普通窗口管理器，则很容易淹没在 Rectangle、Moom、Ankylix、JINRAI 和 Apple 原生功能之间。

Tidy 的成败最终不取决于功能列表有多完整，而取决于用户是否相信：

> 无论窗口怎样临时展开，按一下都能可靠回来。
